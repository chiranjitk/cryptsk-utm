    41→    41→### Why NOT These OSes
    42→    42→
    43→    43→#### FreeBSD — DISQUALIFIED
    44→    44→- **No nftables** — relies on pf (Packet Filter), a completely different firewall paradigm
    45→    45→- **No eBPF/XDP** — the entire modern data-plane acceleration strategy fails
    46→    46→- **Suricata runs in AF_PACKET mode only** — no AF_XDP, significantly lower throughput
    47→    47→- **FRR (FRRouting) has no official FreeBSD port** — BGP/OSPF requires old Quagga forks
    48→    48→- **Docker does not run natively** — service isolation requires FreeBSD jails (different paradigm, less ecosystem)
    49→    49→- **WireGuard support is newer and less battle-tested** than on Linux
    50→    50→- **nDPI, StrongSwan, Kea, and many security tools** have second-class FreeBSD support
    51→    51→- **Verdict**: FreeBSD is excellent for OPNsense/pfSense (which use pf), but **fundamentally incompatible** with a Linux-native eBPF + nftables + Suricata + FRR architecture
    52→    52→
    53→    53→#### Rocky Linux — NOT RECOMMENDED
    54→    54→- **Default firewall is iptables/firewalld**, not nftables-first
    55→    55→- **SELinux adds complexity** for UTM (Suricata, eBPF programs, and custom services require extensive SELinux policy tuning)
    56→    56→- **Kernel is older** (5.14 based, backported) vs Debian/Ubuntu 6.8+
    57→    57→- **eBPF/XDP features lag** behind mainline kernel by 1-2 years
    58→    58→- **RPM ecosystem** — most open-source security tools document Debian/Ubuntu first
    59→    59→- **Good for**: Traditional enterprise servers, not cutting-edge network appliances
    60→    60→
    61→    61→#### Alpine Linux — NOT RECOMMENDED
    62→    62→- **musl libc** — some security tools (Suricata with certain features, Python ML libraries) assume glibc
    63→    63→- **Small community** — less troubleshooting resources for complex UTM issues
    64→    64→- **Limited package selection** — you'd be building many packages from source
    65→    65→- **Good for**: Containers, routers, minimal appliances — not a full UTM platform
    66→    66→
    67→    67→#### Ubuntu 24.04 LTS — CLOSE SECOND
    68→    68→- **Advantages over Debian**: Newer kernel out-of-box, better hardware compatibility, larger community, Snap packages (controversial but useful for some services), cloud-init for deployment
    69→    69→- **Disadvantages**: Heavier base (~4 GB vs ~2 GB), more attack surface (more default services), Snap dependency (some consider it a negative for appliances), slightly faster release cadence can introduce instability
    70→    70→- **Verdict**: Perfectly viable. If your team is more familiar with Ubuntu, use it.
    71→    71→
    72→    72→### RECOMMENDATION: Debian 13 (Trixie)
    73→    73→
    74→    74→**Primary choice: Debian 13 (Trixie)** with Debian 12 (Bookworm) as fallback.
    75→    75→
    76→    76→**Why Debian 13 wins for a UTM appliance:**
    77→    77→1. **nftables is the default** — no iptables legacy baggage
    78→    78→2. **Kernel 6.8+ LTS** — full eBPF/XDP, modern NIC driver support, WireGuard, all current
    79→    79→3. **Smallest attack surface** — minimal default installation, no Snap, no cloud bloat
    80→    80→4. **Predictable** — slow release cycle = fewer surprise breakages in production appliances
    81→    81→5. **Every major open-source security tool tests on Debian first** — Suricata, StrongSwan, FRR, nDPI, Kea, Unbound all have official Debian packages
    82→    82→6. **glibc** — full compatibility with all Python ML libraries (PyTorch, TensorFlow, ONNX Runtime)
    83→    83→7. **Docker/Podman** — first-class support for service isolation
    84→    84→8. **Proven in production** — pfSense CE was Debian-based, OPNsense is the only major FreeBSD holdout
    85→    85→9. **Pure FOSS** — no proprietary components, no telemetry, no licensing games
    86→    86→10. **Long-term stability** — Debian releases are the gold standard for "set it and forget it" servers
    87→    87→
    88→    88→**Kernel Requirements (must backport if not in default kernel):**
    89→    89→```
    90→    90→- eBPF (BPF_PROG_TYPE_XDP, BPF_PROG_TYPE_CGROUP_SKB)
    91→    91→- XDP (native, redirect, pass, drop actions)
    92→    92→- nftables with all extensions (conntrack, tproxy, hash, limits)
    93→    93→- WireGuard (kernel module or built-in)
    94→    94→- AF_XDP (for future 10G+ optimization)
    95→    95→- Netfilter conntrack enhancements (max, timeout tuning)
    96→    96→- tc (traffic control) with FQ_CoDel, CAKE, HTB qdiscs
    97→    97→```
    98→    98→
    99→    99→**If Debian 13 is not yet stable at your build time, use Debian 12 (Bookworm) + backports kernel (6.8+).**

   187→   187→## ARCHITECTURE
   188→   188→
   189→   189→### Data Plane (Packet Processing Pipeline)
   190→   190→```
   191→   191→NIC → XDP (early drop/rate-limit) → eBPF (flow export, metadata)
   192→   192→  → nftables (L3/L4 firewall + NAT)
   193→   193→  → conntrack (state tracking)
   194→   194→  → TPROXY/SQUID (if proxy or SSL inspection enabled for this flow)
   195→   195→  → nDPI (application classification)
   196→   196→  → Suricata IPS (inline mode, if policy attached)
   197→   197→  → tc/QoS (traffic shaping)
   198→   198→  → Output NIC
   199→   199→```
   200→   200→
   201→   201→**Key Design Decisions:**
   202→   202→- XDP handles **syn-flood protection, basic L3/L4 ACLs, and rate-limiting** at line rate before kernel
   203→   203→- nftables handles **all stateful firewall + NAT** rules
   204→   204→- TPROXY redirects selected traffic to Squid/Coraza for proxy/WAF
   205→   205→- nDPI runs as **a helper** to Suricata or standalone for app classification
   206→   206→- Suricata runs in **inline mode** with AF_PACKET (or AF_XDP in future)
   207→   207→- tc handles **all QoS/shaping** at egress
   208→   208→
   209→   209→### Control Plane
   210→   210→```
   211→   211→Next.js UI ←→ Go REST API ←→ PostgreSQL (config store)
   212→   212→                                 ←→ Redis (cache, sessions, pub/sub)
   213→   213→                                 ←→ System Services (via systemd / Docker)
   214→   214→```
   215→   215→
   216→   216→**Key Design Decisions:**
   217→   217→- All configuration is **database-driven** (PostgreSQL)
   218→   218→- Changes are deployed to system services via **configuration generators** (Go templates → service config files)
   219→   219→- Real-time UI updates via **WebSocket** (Redis pub/sub → Go → WebSocket)
   220→   220→- API-first: **every UI action calls the same REST API**
   221→   221→
   222→   222→### AI Layer (Simplified)
   223→   223→```
   224→   224→Log/Flow Data → Redis Queue → Python Feature Extractor
   225→   225→  → ONNX Runtime Inference → Risk Score → Action (alert/block/quarantine)
   226→   226→  → PostgreSQL (inference log) → Feedback Loop
   227→   227→```

  1550→  1550→## FINAL NOTES
  1551→  1551→
  1552→  1552→1. **This is a 24-month roadmap, not a 6-month one.** The original MD tried to build a Fortinet-killer in one shot. That's not realistic for a startup. Phase 1 alone (6 months) gives you a deployable product.
  1553→  1553→
  1554→  1554→2. **Open source is your advantage, not your weakness.** Fortinet and Sophos spend millions on proprietary engines that you get for free. Your job is to integrate them well, build a great UI, and sell on price + transparency.
  1555→  1555→
  1556→  1556→3. **AI is a marathon, not a sprint.** Don't build 13 AI models on day one. Build rule-based + statistical detection first. Add ML when you have real traffic data from deployed units.
  1557→  1557→
  1558→  1558→4. **The URL filtering gap is your biggest vulnerability.** Invest early in aggregating free lists and building a simple categorization system. Consider a hybrid model: free lists + optional paid Webshrinker API for customers who need better coverage.
  1559→  1559→
  1560→  1560→5. **Go, not Java.** For an appliance, a single-binary Go backend is dramatically simpler to deploy, update, and debug than a Java Spring Boot application.
  1561→  1561→
  1562→  1562→6. **Compete on UX, not on security depth.** A Next.js dashboard that's 10x easier to use than FortiOS is a genuine competitive advantage. Small enterprise admins are not security experts — they want something that works out of the box with sensible defaults.
