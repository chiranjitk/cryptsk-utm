     1→# Endpoints — Cryptsk Console
     2→
     3→> TL;DR: Complete Phase 1 endpoint catalog. Paths are **LOCKED** from PROJECT_MEMORY §7.2 — expand here,
     4→> never rename. Every response uses the shared envelope; every mutation is audited and version-snapshotted
     5→> by `lib/api/handler.ts` (see [./API_STANDARDS.md](./API_STANDARDS.md)).
     6→
     7→Related: [../00-PROJECT-MEMORY/PROJECT_MEMORY.md](../00-PROJECT-MEMORY/PROJECT_MEMORY.md) §7 (contract of record) ·
     8→[./API_STANDARDS.md](./API_STANDARDS.md) (envelope, errors, RBAC matrix) ·
     9→[../03-DATABASE/SCHEMA.md](../03-DATABASE/SCHEMA.md) (field names + JSON shapes) ·
    10→[../02-ARCHITECTURE/ARCHITECTURE.md](../02-ARCHITECTURE/ARCHITECTURE.md)
    11→
    12→**Legend**
    13→
    14→- Role floors come from the RBAC matrix in API_STANDARDS §2. Ladder:
    15→  `helpdesk < soc_analyst < network_admin = security_admin < tenant_admin < super_admin`.
    16→  L3 is peer level (either L3 role satisfies the other's floor). `auditor` may call any GET regardless of
    17→  floor but no mutation. `api_service` needs a key scope covering the capability (`read`/`write`/`admin`).
    18→- `Audit?` = yes means the shared handler writes an `audit_log` row (`<objectType>.<verb>`) plus a
    19→  `config_versions` snapshot for the affected section. Reads are never audited.
    20→- All timestamps are ISO-8601 UTC. All bodies camelCase, matching SCHEMA.md TS field names. Flat JSON
    21→  objects in examples are wrapped across lines for readability; every example is complete JSON.

    33→`POST /api/v1/auth/login` — request, then `200`:
    34→
    35→```json
    36→{ "username": "admin", "password": "CorrectHorse1!" }
    37→```
    38→
    39→```json
    40→{
    41→  "data": {
    42→    "user": {
    43→      "id": 1, "tenantId": 1, "username": "admin", "role": "super_admin",
    44→      "email": "admin@corp.local", "isActive": true, "totpEnabled": false,
    45→      "lastLoginAt": "2026-11-04T18:22:31.000Z"
    46→    },
    47→    "permissions": { "read": true, "write": true, "admin": true }
    48→  }
    49→}
    50→```
    51→
    52→Response carries `Set-Cookie: cryptsk_token=<jwt>; HttpOnly; Path=/; Max-Age=28800; SameSite=Lax` —
    53→httpOnly, never parsed in client JS. `totpEnabled` is derived from a non-null `totpSecret` (not a column).
    54→Wrong credentials → `401 UNAUTHORIZED` and an audit row with `result: "failure"`.
    55→
    56→Errors worth expecting: `401` bad credentials; `429` login throttled by the auth-settings lockout policy.

   182→`POST /api/v1/address-groups` — request, then `201` (`memberIds` are `address_objects.id`; groups do not nest):

   185→{ "name": "guest-subnets", "memberIds": [3, 4, 7], "description": "All guest ranges" }

   200→## 5. Firewall — Rules & NAT
   201→
   202→| METHOD | Path | Purpose | Role floor | Audit? |
   203→|---|---|---|---|---|
   204→| GET | `/api/v1/firewall-rules` | Ordered list (`?zone=&search=`) | soc_analyst | no |
   205→| POST | `/api/v1/firewall-rules` | Create rule | security_admin | yes |

   207→| PUT | `/api/v1/firewall-rules/{id}` | Replace rule (echo `updatedAt`) | security_admin | yes |
   208→| DELETE | `/api/v1/firewall-rules/{id}` | Delete rule | security_admin | yes |
   209→| PATCH | `/api/v1/firewall-rules/{id}/toggle` | Enable/disable, body `{enabled}` | security_admin | yes |
   210→| POST | `/api/v1/firewall-rules/reorder` | Full order write, body `{orderedIds}` | security_admin | yes |
   211→| GET | `/api/v1/firewall-rules/{id}/hits` | Hit counters | soc_analyst | no |
   212→| POST | `/api/v1/firewall-rules/{id}/hits/reset` | Reset per-rule counters | security_admin | yes |
   213→| POST | `/api/v1/firewall-rules/validate` | Shadow/conflict check, no persist | security_admin | no |
   214→| POST | `/api/v1/firewall-rules/import` | `{format: "json"\|"csv", payload}` | security_admin | yes |
   215→| GET | `/api/v1/firewall-rules/export?format=` | Export json/csv | soc_analyst | no |
   216→| GET | `/api/v1/nat-rules` | List NAT rules | soc_analyst | no |
   217→| POST | `/api/v1/nat-rules` | Create NAT rule | security_admin | yes |
   218→| PUT | `/api/v1/nat-rules/{id}` | Update NAT rule | security_admin | yes |
   219→| DELETE | `/api/v1/nat-rules/{id}` | Delete NAT rule | security_admin | yes |
   220→| PATCH | `/api/v1/nat-rules/{id}/toggle` | `{enabled}` — optimistic toggle | security_admin | yes |
   221→| POST | `/api/v1/nat-rules/reorder` | `{orderedIds: number[]}` full order | security_admin | yes |
   222→
   223→`POST /api/v1/firewall-rules` — `srcAddrIds`/`dstAddrIds` mix address-object and address-group ids;
   224→`serviceIds` mixes service-object and service-group ids (logical references, service-layer integrity).
   225→Omitted `position` appends the rule last (explicit placement goes through `/reorder`):
   226→
   227→```json
   228→{
   229→  "name": "block-guest-to-corp", "description": "Guests must not reach corp subnets",
   230→  "enabled": true, "position": 4,
   231→  "srcZoneIds": [3], "dstZoneIds": [1],
   232→  "srcAddrIds": [6, 12], "dstAddrIds": [2, 14],
   233→  "serviceIds": [1, 8], "applicationIds": [], "userIds": [], "scheduleId": null,
   234→  "action": "deny", "logging": "summary",
   235→  "connLimit": 500, "rateLimit": 100, "synProtection": false, "synThreshold": null,
   236→  "ipsPolicyId": null, "qosPolicyId": null,
   237→  "tags": ["guest", "guardrail"], "comment": "SOC ticket 4412"
   238→}
   239→```
   240→
   241→`201` response:
   242→
   243→```json
   244→{
   245→  "data": {
   246→    "id": 12, "tenantId": 1,
   247→    "name": "block-guest-to-corp", "description": "Guests must not reach corp subnets",
   248→    "enabled": true, "position": 4,
   249→    "srcZoneIds": [3], "dstZoneIds": [1],
   250→    "srcAddrIds": [6, 12], "dstAddrIds": [2, 14],
   251→    "serviceIds": [1, 8], "applicationIds": [], "userIds": [], "scheduleId": null,
   252→    "action": "deny", "logging": "summary",
   253→    "connLimit": 500, "rateLimit": 100, "synProtection": false, "synThreshold": null,
   254→    "ipsPolicyId": null, "qosPolicyId": null,
   255→    "tags": ["guest", "guardrail"], "comment": "SOC ticket 4412",
   256→    "hitCount": 0, "lastHitAt": null,
   257→    "createdAt": "2026-11-05T09:05:00.000Z", "updatedAt": "2026-11-05T09:05:00.000Z"
   258→  }
   259→}
   260→```
   261→
   262→`POST /api/v1/firewall-rules/validate` — candidate rule body (same shape, no `id`); optional `excludeRuleId`
   263→when re-validating an edit of an existing rule. `200` with conflict list; `ok` is `true` when `conflicts` is
   264→empty. `reason` is `"shadowed_by"` (candidate made unreachable by an earlier rule) or `"conflicts_with"`
   265→(overlapping match, contradictory action):
   266→
   267→```json
   268→{
   269→  "data": {
   270→    "ok": false,
   271→    "conflicts": [
   272→      { "ruleId": 7, "ruleName": "allow-guest-web", "reason": "shadowed_by", "withRuleId": 3, "withRuleName": "permit-all-lan" },
   273→      { "ruleId": 12, "ruleName": "block-guest-to-corp", "reason": "conflicts_with", "withRuleId": 9, "withRuleName": "guest-web-allow" }
   274→    ]
   275→  }
   276→}
   277→```
   278→
   279→`POST /api/v1/firewall-rules/reorder` — full ordered id array, then `200`:
   280→
   281→```json
   282→{ "orderedIds": [12, 3, 7, 9, 1] }
   283→```
   284→
   285→```json
   286→{
   287→  "data": {
   288→    "rules": [
   289→      { "id": 12, "position": 1 }, { "id": 3, "position": 2 }, { "id": 7, "position": 3 }, { "id": 9, "position": 4 }, { "id": 1, "position": 5 }
   290→    ]
   291→  }
   292→}
   293→```
   294→
   295→`POST /api/v1/nat-rules` — DNAT port forward; `201` wraps the created `NatRule` row (same fields plus
   296→`id`, `tenantId`, `hitCount`, `createdAt`) in `data`:
   297→
   298→```json
   299→{
   300→  "name": "web-portal-forward", "position": 2, "type": "dnat", "enabled": true,
   301→  "srcAddrIds": [], "dstAddrIds": [5], "serviceIds": [2], "outgoingIface": "wan0",
   302→  "translatedSrc": null, "translatedDst": "192.168.10.60", "translatedPort": 8080,
   303→  "comment": "Portal reverse proxy"
   304→}
   305→```
   306→
   307→> Gap: the spec marks rule hit counters as resettable, but §7.2 locks only `GET /{id}/hits` — no reset path.
   308→> Gap: NAT has no `/toggle` or `/reorder` endpoint (firewall rules have both); NAT reordering must use
   309→> `PUT /nat-rules/{id}` with `position` until a reorder path is added. Needs PROJECT_MEMORY update.
   310→
   311→Errors worth expecting: `400` invalid action/logging enums, malformed reorder array (missing/duplicate ids);
   312→`409` stale `updatedAt` on PUT (optimistic concurrency, API_STANDARDS §8); `409` deleting an object still
   313→referenced by rules via `srcAddrIds`-style arrays.

   367→`POST /api/v1/vpn/configs/3/client-bundle` — `200` with the full file as text; the client triggers a

   369→
   370→```json
   371→{
   372→  "data": {
   373→    "filename": "wg-remote-access-alice.conf",
   374→    "contentType": "text/plain",
   375→    "content": "[Interface]\nPrivateKey = <client-private-key>\nAddress = 10.99.0.24/32\nDNS = 10.10.0.1\n\n[Peer]\nPublicKey = <server-public-key>\nEndpoint = vpn.corp.example:51820\nAllowedIPs = 0.0.0.0/0\nPersistentKeepalive = 25\n"
   376→  }
   377→}
   378→```
   379→
   380→Available for remote-access types (`wireguard_remote`, `ipsec_remote`, `openvpn`); other types → `409`.
   381→`GET /vpn/configs/{id}/status` returns
   382→`{data: {status, statusMessage, peers: [{name, handshakeSec, transferIn, transferOut}], dpdSec}}` for s2s types.
